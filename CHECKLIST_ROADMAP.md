## 1. Executive Summary

The Turing Machine IDE is a feature-rich browser-based learning tool supporting three distinct diagramming/simulation modes:

| Mode | Description |
|------|-------------|
| **5-Tuple (Standard)** | Classical Turing machine — state graph with rules (q, a, a′, d, q′) |
| **4-Tuple State Graph** | Post-Turing quadruples (q, a, C, q′) — write or move per step |
| **4-Tuple Operational (VTM)** | Visual flowchart of macro-operations (START, l, r, L, R, [a], FINISH) |

### Architecture at a Glance

```
src/
  types/turing.ts           — Type system: nodes, edges, rules, session, tape
  store/useTuringStore.ts   — Zustand store (single source of truth, persisted)
  store/demoProjects.ts     — 3 built-in demo sessions
  engine/
    simulator.ts            — Step execution (5-tuple, 4-tuple, VTM), undo history
    transpiler.ts           — 5⟷4 tuple conversion, VTM→4-tuple compilation
    validator.ts            — Static analysis (determinism, reachability, alphabet)
    exporter.ts             — JSON, LaTeX, PlantUML, Markdown export
    engine.test.ts          — `jiti`-based unit test suite
  components/
    canvas/                 — TuringCanvas (ReactFlow), StateNode, OperationNode,
                              CustomTransitionEdge, RuleModal
    inspector/              — TupleTableEditor, MatrixEditor, DiagnosticsPanel
    navbar/                 — HeaderNavbar, ExportModal
    sidebar/                — AlphabetBuilder, SessionManagerDrawer
    tape/                   — InfiniteTapeDock, DebuggerControls, BatchTestRunner
```

## 4. Edge Cases & Potential Pitfalls

### 4.1 Tape Boundary Issues

| Scenario | Current Behavior | Expected Behavior |
|----------|-----------------|-------------------|
| Head at position 0, move L | Head goes to -1, tape at -1 reads blank | ✅ Correct (infinite tape) |
| Head at negative position | Display recenters; `rangeOffset=0` on head change | ✅ Mostly correct |
| Very long tape (10,000+ cells) | Only 25 cells rendered | ✅ OK — uses virtual window |
| `setTapeString` with multi-char symbols | Indexes by char → breaks | 🔴 Must handle symbol tokenization |
| Tape with blank holes (sparse) | SparseTape correctly reads blank for missing | ✅ Correct |

### 4.2 Infinite Loop Detection

- **Current:** None. `runTestCase` aborts at `maxSteps=10000`. Interactive mode runs forever.
- **Risk:** A buggy machine in continuous run mode can freeze the browser tab.
- **Recommended:** Detect repeated configuration `(currentNodeId, headPosition, md5(tape))`. Flag as `status = 'error'` with message after N periodic matches.
- **Pitfall:** Tape is infinite and sparse — full hash is expensive. Use a sliding window of last 50 configurations.

### 4.3 Alphabet Refactoring

- **Current gaps:** `refactorSymbol` updates `rules5`, `rules4`, `edges`, `testCases`, but misses `nodes[].data.symbolToWrite` (WRITE_SYM operational nodes).
- **Pitfall:** If the blank symbol character is changed, the `initialTape` sparse keys still reference old blank positions implicitly (absence = blank). This is safe but renaming blank to a non-conventional character (e.g., `λ`) requires careful propagation.
- **Pitfall:** Renaming a symbol to an existing one silently merges them. Should add uniqueness check.

### 4.4 Conversion Fidelity: 5-Tuple ↔ 4-Tuple

| Conversion | Corner Case | Current Behavior |
|------------|-------------|-----------------|
| 5→4 when `writeSymbol === readSymbol` and `move !== 'N'` | Simple 1-step shift: correct | ✅ |
| 5→4 when `move === 'N'` | Write-only without move: correct | ✅ |
| 5→4 when write ≠ read AND move ≠ N | Creates auxiliary state `q_aux_N` | ✅ Correct auxiliary state |
| 4→5 for movement rules | Sets `writeSymbol = readSymbol` | ✅ Idempotent for movement |
| 4→5 for write rules | Sets `move = 'N'` | ✅ Correct |
| Roundtrip 5→4→5 | Auxiliary states remain in 5-tuple form | 🟡 Extra states never collapsed |
| Auxiliary state IDs collide | `q_aux_1`, `q_aux_2` ... — not unique across projects | 🟡 Low risk; fresh counter per conversion |

### 4.5 State ID / Label Collisions

- `addStateNode` generates IDs as `q0`, `q1`, ... by counting existing `stateNode`s. If a node with ID `q1` already exists (from a previous session import or demo), a new node also gets ID `q1` → silent duplicate.
- **Fix:** Use a UUID or timestamp-based ID, not a simple counter.
- Same risk in `addOperationNode` which generates `op_shift_l_3` etc. by counting `nodes.length`.

### 4.6 Non-Deterministic Branching

- Simulator uses `.find()` (first matching rule). Non-deterministic machines silently pick the first match, giving misleading results.
- Validator correctly flags non-determinism as an error — but only after the user discovers the wrong output.
- Recommended: add a warning in the debugger status bar when a non-deterministic rule is selected during stepping.

### 4.7 Operational VTM Complement Condition (`¬a`)

- Validator checks `r.isComplement && r.readSymbol !== sym` for outgoing edges.
- Transpiler: `compileOperationalDiagramTo4Tuples` processes `isComplement` correctly in edge matching.
- **Risk:** If multiple edges have overlapping complement/wildcard conditions, the compiler picks the first match via `outgoing.find()`. This is inconsistent with actual complement semantics where ALL non-matching symbols should route that edge.
- **Fix:** When compiling, for each symbol, check `isComplement` by explicitly testing `r.readSymbol !== sym` per symbol in the alphabet, not relying on `find()`.
